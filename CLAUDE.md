## Commands

```bash
npm run build                     # ng build -> builds kometa-ui (ng-packagr) into dist/kometa-ui
npm start                         # ng serve demo, port 4200 (also .claude/launch.json "demo")
npm test                          # ng test (vitest + jsdom); library only, the demo has no specs
npx ng test kometa-ui --watch=false --include='**/kometa-button.spec.ts'   # one spec file
npx ng build demo                 # production build of the demo
```

Pin `jsdom@^28` and `vitest@^4`. Newer majors (jsdom 30, vitest 5) fail 8 specs, e.g. `k-time.spec.ts` focus behaviour.

## Architecture

- **Two projects** in one workspace: `projects/kometa-ui` (the library) and `projects/demo` (showcase app).
- The demo imports the library **from source**: `tsconfig.json` maps `kometa-ui` to `projects/kometa-ui/src/public-api.ts`, so no library rebuild is needed while developing. Its `styles.scss` `@use`s the library styles by relative path.
- **Single entry point.** `src/public-api.ts` is a flat list of `export *` per component file plus `provideKometaUi`. It was generated by a shell loop; when you add a `kometa-*.ts` file, add its export by hand. The source app imported each component by its own path to keep initial chunks small; here the barrel relies on `sideEffects: false`.
- Element selectors use the `k-` prefix (`<k-button>`, `button[k-halo]`); files, classes and CSS vars keep `kometa-`/`Kometa`. Components are standalone and OnPush, mostly with default (emulated) encapsulation (button, drawer, rows and table use `ViewEncapsulation.None`), with styles written inline using `:where()` so consumer CSS wins without specificity fights. They read CSS custom properties from `projects/kometa-ui/styles/tokens.scss` (`--amber`, `--bg`, `--text`...), including light/dark schemes.
- No PrimeNG (removed 2026-11-11). `provideKometaUi()` (`lib/provide-kometa-ui.ts`) is empty, kept so app configs need no change. `k-tray` listens to `KometaConfirmationService` (`confirm({ header, message, acceptLabel, rejectLabel, acceptButtonProps, accept, reject })`). Outputs: `k-button` `(clicked)`, `k-drawer` `(opened)` / `(closing)` / `(kometaSheetClosed)`.
- **SCSS everywhere.** Styles files are `.scss` and `inlineStyleLanguage` is `scss`; the one exception is `styles/kometa-theme.css`, a Tailwind v4 `@theme` file that Tailwind must read as plain CSS. Tests compile inline styles through Sass too, which drops quotes in attribute selectors (`[data-surface=glass]`), so specs that regex-match component CSS must accept both forms.
- **CSS layer order is a contract:** the consuming app's stylesheet must `@use 'kometa-ui/styles/layers'` first (`@layer theme, base, legacy, components, utilities;`, matching `KOMETA_LAYER_ORDER`). Sass forbids a bare `@layer` statement before `@use`, hence the file. The demo's `styles.scss` does this.
- Styles and fonts ship as library assets (`ng-package.json` `assets: ["styles/**/*"]`) and are used by consumers as `@use 'kometa-ui/styles/<name>'`.
- `lib/test-setup.ts` stubs `matchMedia` and `ResizeObserver` for jsdom; it is wired in `angular.json` as the test `setupFiles`.

## Known gaps

- The demo is a docs site with three layouts, picked by `layout()` in `app.ts`: `home` (the welcome page, `app/home/`, full width with no sidebar; the default for an empty hash), `wide` (the Screens) and `docs` (sidebar with filter, one page per component, 63 of them plus the two guides (`#button`, sections deep-link as `#button/severity`), an "On this page" list with scroll-spy, prev/next). Ctrl+K or `/` opens a command palette (`<dialog>` in `app.html`); `log.set()` writes to the event ticker at the bottom left. The page list is `nav` in `app.ts`; `apis` there maps each page to its classes for the Import line and the API table, which is read from Angular's `ɵcmp`/`ɵdir` metadata (names and kinds only, no types or defaults). Each example is an `<app-doc id heading about>` (`app/docs.ts`) with a preview toolbar (canvas: plain/grid/dots; width: full/tablet/phone) and code tabs. The HTML tab is cut from `app.html` itself, imported as text, so snippets cannot drift; the TypeScript and SCSS tabs are `// #region page/id` … `// #endregion` blocks in `app.ts` / `app.scss` (also imported as text: a `.ts` file needs `// @ts-ignore` on the `with { loader: 'text' }` import). `ng serve` does not refresh text imports when the file changes, so a code tab can lag its live demo until the dev server restarts; `ng build` is always current. A self-closing `<app-doc />` must pass `[code]`. **Screens** (`app/screens/<name>/`, one standalone component each, mock data in its `.ts`) are whole pages built from many components; `screens/sources.ts` reads their three files as text for `[files]`, and each exports `USES` (docs page ids) for its "Built with" list. To add a screen: the folder, a `sources.ts` entry, a `nav` entry under Screens, `screenUses` and a `@case` in `app.html`. `k-tabbar` with `link` and `k-row` with `link` need a router, which the demo does not provide, so they are shown without links. `k-suggest` draws a bare `<input>` that the host styles; the demo wraps it in `.field`. To add a page: a `@case ('id')` block in `app.html` (`<app-doc>` ids unique within it), a `nav` entry and an `apis` entry in `app.ts`. Most pages carry a `basic` example, one per option added after the first version, and a "Customizing" example that sets the component's CSS custom properties inline; Theming lists the pattern. `k-tray` has no options example because the app-wide `<k-tray>` at the bottom of `app.html` would clash with a second one.
- `kometa-theme.css` (the Tailwind v4 `@theme inline` mapping) is shipped but not imported by the demo.
